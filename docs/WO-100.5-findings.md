## 1. Phase 0 — `NPC_NAI`, and why it is not the answer

### 1.1 The live scoreboard

One session, one save, four probe bodies, all spawned with the same roster soul
guid (`ttkc_man_26`, the `KCD2MP.faceFallback` entry). The decisive measurement
is the engine's own line
`Skirmish event: HitTarget on Dude (target <name>)` — 20 of them in a
71,829-line log, counted across the whole file (**observed**):

| body | class | spawn | `HitTarget` |
|---|---|---|---|
| `wo1005_A_nai` | `NPC_NAI` | `System.SpawnEntity` | **0** |
| `wo1005_B_npc` | `NPC` | `System.SpawnEntity` | 2 |
| `wo1005_C_noai` | `NPC` | `XGenAI`, `NoAI=true` | **7** |
| `wo1005_E_ctrl` | `NPC` | `XGenAI` | 0 (never hit; it was the *witness*) |

The maintainer landed "a shitload of hits" on the `NPC_NAI` body across two
trials, one at night and one at 14:00. **The skirmish system booked none of
them.**

### 1.2 Item 1 — perception. The cost is bigger than the question

`bWH_PerceptibleObject` being absent is the headline, but it understates it. An
`NPC_NAI` body is not merely invisible to the perception system; it is outside
the combat bookkeeping. Hitting it produces exactly one thing — its own
`COMBAT_VICTIM_SCREAM_RECEIVED_HIT` dialogue, three log lines — and no
`HitTarget`, no witness, no crime, no guard (**observed**, twice).

Hitting the ordinary `NPC` beside it produced 37 lines: `SVEDEK_VIDI_JAK_NPC_
DOSTALO_ZASAH` (witness sees an NPC take a hit), `OBET_REPORTUJE_STRAZI_
(ASSAULT__UNARMED)` (victim reports to a guard), skirmish soul add/remove,
`alerted` tags, and guard `ttkc_man_23` running crime barks through to
`STRAZ_PATRA_NA_MISTE_CINU_A_ROZPOZNA_HRACE`.

**So with the class swap on, a ghost stops being a crime victim.** That
directly reverses WO-68's shipped behaviour ("ghosts join vanilla
crime/reputation"), which is far more than the WO's framing anticipated. It is
the reason the toggle defaults off.

### 1.3 Item 4 — the class swap does not survive the ghost path

Not a plumbing bug on our side. The engine substitutes the class
(**observed**, 3 of 3):

```
XGenAIModule.SpawnEntity{ClassName="NPC_NAI", ...}              -> built NPC
XGenAIModule.SpawnEntity{ClassName="NPC_NAI", NoAI=true, ...}   -> built NPC
System.SpawnEntity{class="NPC_NAI", ...}                        -> built NPC_NAI
```

And `System.SpawnEntity` is the path that does **not** bind `SharedSoulGuid`
(WO-22). So the two spawn APIs offer **the class or the soul, never both**.
Since WO-22, a soulless ghost is the A1 unconsciousness bug; the soul is not
optional. The class swap is therefore unreachable on the ghost path by
construction, and the primary spawn would silently ignore it.

`mp_ghost_nai` still ships, because the WO asked for it, but
`KCD2MP_SetGhostNai(true)` prints that finding every time it is switched on
rather than letting a toggle quietly do nothing.

### 1.4 `NoAI=true` — the lever the phase was actually after

`NoAI` is a shipped parameter of `XGenAIModule.SpawnEntity`, listed in
Warhorse's own scriptbind doc beside `Name` / `ClassName` / `SharedSoulGuid` /
`SchedulerProxyName` — the same doc WO-22 read the flat-table shape out of. It
keeps everything the class swap threw away and still removes the brain
(**observed**):

| | `NPC_NAI` | `NPC` + `NoAI=true` | `NPC` |
|---|---|---|---|
| entity class | `NPC_NAI` | `NPC` | `NPC` |
| soul binds (XGenAI path) | unreachable (§1.3) | **yes** | yes |
| `HitTarget` registrations | 0 | **7** | 2 |
| witnessed / reported as a crime | no | **yes** | yes |
| `SituationController` registrations | 0 | **0** | 3 |
| `npc_basic_scheduler` behaviour tree | 0 | **0** | present |
| self-initiated dialogue (gossip, greeting) | 0 | **0** | 7 |
| engine line when hit | scream only | `'<name>': no valid reaction found` | full reaction |

Ships as `mp_ghost_noai_on` / `mp_ghost_noai_off`, argless, **default off**.
Off is byte-identical to every previous session: the `NoAI` key is added to the
spawn table only when the toggle is on.

### 1.5 Item 2 — situations, and what it means for WO-99.5

Situation registration goes to **zero** for both `NPC_NAI` and `NoAI=true`
(**observed**). But WO-99.5's script-context crime fix is **not** made dead
weight, and the reason is §1.4's table: the body we will actually ship
(`NPC` + `NoAI`) is still a full crime participant — witnessed, reported,
guards dispatched. The script contexts are what stop a *ghost* being treated as
a townsman for crime purposes; `NoAI` removes its *initiative*, not its civic
standing. Two mechanisms, two jobs. Stated explicitly, as asked.

### 1.6 Item 3 — faction

No `does not have a faction` line from any of the four bodies (**observed**).
WO-100 §10.6's caveat is confirmed and bounded: the spam is a *bare* spawn
symptom, and a bound soul is sufficient to remove it. The ghost path already
binds one.

### 1.7 Corrections to record

* `wo1005_E_ctrl` "running away" after being punched was it **witnessing** the
  assault on the body beside it, not reacting to its own. It has zero
  `HitTarget` lines. Field impressions and the skirmish ledger disagreed, and

* There is no `NPC_NAI_Female` in this build (**code-verified**: `WHGame.dll`
  registers `NPC_Female` and `NPC_NAI` and nothing else matching `NPC_*`).
  Moot today — since WO-69 `KCD2MP_PickFaceForPlayer` always returns `NPC` —
  but a future female roster entry must not take the swap path.
* `entity.AI` read non-nil on the `NPC_NAI` body, as WO-100 §10.6 warned. Not
  used as evidence.

## 2. Phase 1 — the first combat write

### 2.1 Item 1 — the second call site, and two corrections

`0x76500` has **16 direct `E8` call sites** (code-verified, scanned over
`.text` with the `.pdata` function table for bounds). Three were read:

| site | what it pins |
|---|---|
| `0x1268C4` `C_CombatAutomationBlock::FireAction` | WO-100's original |
| `0x76CE5` | a 4-arg wrapper `(actor, out, int, byte)` that hardcodes `r8b=6` and `[rsp+0x28]=-1` and forwards the other two — this is what pins arg4 as the int and arg5 as the byte |
| `0x47E13` | `rcx` is the combat actor: the same basic block reads `[rcx+0x2F0]` (the model) and branches on `[model+0xA20]`/`[model+0x9E0]` to pick `r8b = 4` or `1` |

Confirmed signature:

```
void* RequestAction(I_CombatActor*, void** outAction,
                    uint8 actionTypeId, int32 zoneId,
                    uint8 handSlot, int32 param6)
```

**Correction 1.** WO-100 recorded the last two arguments as one
`int64 packed(strength, -1)`. They are two separate slots — a byte at
`[rsp+0x20]` and a DWORD at `[rsp+0x28]`.

**Correction 2, the one that mattered.** WO-100 handed over `0xF4C20` as "the
property setter, `(propertyBase, value, flag)`". **It is not a property setter**
(code-verified):

* 25 of its 26 direct call sites pass the *same* object, `model + 0xEE8`.
* Its body is `if (((uint8*)obj)[8 + index] == value) return;` — literally
  `cmp byte ptr [rbp + rsi + 8], dil` with `rbp = movsxd(edx)`. The second
  argument **indexes a byte array**.

Real signature: `SetFlag(void* flagsObj, int32 index, uint8 value)`, against a
flag-array object at `model + 0xEE8` with a vptr at `+0x00` and the bytes at
`+0x08`. Following WO-100's note would have written a byte at
`propBase + 8 + value` — the project's standing trap, in write form.

So the first write became the shipped call with the shipped arguments:
`C_CombatPlayerController::SetStandardGuardRequest` (`0x33F110`) does exactly
`SetFlag(model + 0xEE8, 0, 1)`.

### 2.2 Items 2 and 3 — the write. **LIVE-VERIFIED**

```
CW: model=0000025162161200 known-answer OK (model+0x200 names itself "RequestedAtkZone")
CW: prologue OK for SetFlag(0xF4C20) at CombatModule+0xF4C20 (15 bytes)
CW-SET: calling SetFlag(obj=00000251621620E8, index=0, value=1) -- flag[0] reads 0 before
CW-SET: flag[0] before=0 after=1 wanted=1 -- TOOK (read back at one byte, the correct width)
```

`obj == model + 0xEE8` exactly. Read back at **one byte**, which is the width
the trap in WO-100 §10.5 is about. No crash.

**The strongest single piece of evidence is one nobody asked for:** thirteen
seconds later, before the next command, `flag[0]` read `0` again. The game
*consumed* the write. That distinguishes "we changed a byte" from "we reached a
live system" and it is the check the WO's read-back alone would not have made.

### 2.3 Item 4 — the block action. **REFUSED, and the blocker is specific**

Fired on the player, in a real fight, prologue verified:

| `actionType` | `zone` | `hand` | result |
|---|---|---|---|
| 6 | 0,1,2,3,5 | 0 | null, every time |
| 6 | 1 | 1 | null |

Six calls, six nulls, no crash (**observed**). **The refusal is not the
arguments.**

And a correction to my own probe, caught by checking rather than assuming: the
line `"Automated block was not triggered - anim queue failed!"` is printed by
the shipped **caller** (`0x126800`), not by `0x76500`. A direct call cannot
produce it — zero occurrences in the whole 71,829-line log across all six
refused calls. The null return is the entire report. WO-100 §4.2's claim that
"the engine already reports this action's failure at this level" is wrong: it
reports it one level *up*, in code we are not running.

**Not tried: an NPC.** Every shipped call site fires on an AI-driven body, and
`C_Player` has already been caught overriding combat behaviour in this exact
area (WO-100 §10.3, `GetPseudoSpeed`). That is the obvious next step and it did
not happen because the fight ended. **WO-101 candidate, top of the list.**

Per item 6, no attack was attempted: block behaved unexpectedly, so the
sequence stopped there.

## 3. Phase 2 — locomotion replication

Built as WO-100 §6.1 designed it. Nothing here is live-verified; 33 synthetic
checks and 127 agent tests are green.

* **Wire.** Position/Ghost flag bit `0x04` adds five bytes,
  `[pace:1][dir:1][stance:1][animSpeedCenti:2]`. Additive in WO-99's STALE-bit
  shape: the length dispatch takes the old length or the new one, a sender with
  no reading emits the old 17-byte packet, and `KCD2MP_UpdateGhost`'s four new
  parameters arrive `nil` from an older agent. **Absence is the signal** — no
  probe, no negotiation.
* **Enums keyed on names**, mirrored by number across `mannequin_read.h`,
  `Protocol.cs` and `kdcmp.lua`. An ordinal this build cannot name is counted
  and logged once per distinct value (`MP-ANIM reject=unknown-ordinal`), never
  silently mapped to a neighbour.
* **Source.** Lua has no tag reader (WO-100 §1.4), so the sender reads natively
  over a new pipe command `0x09`/`0x85` — the same chain and the same five
  refusal gates as WO-100's probe, minus every log line, because this runs at
  the position stream's cadence. Switched off for the session after 20
  consecutive refusals, with one line saying so, rather than paying a pipe round
  trip forever to re-learn that the DLL is older than the agent.
* **No debouncing.** WO-100 §10.2 settled it live. `stopLegLeft`/`stopLegRight`
  are never published.
* **No third smoothing implementation.** Two already exist (WO-100 §7).

### 3.1 `pseudoSpeed` — the decision, and why

**Not taken through the vtable override.** The player always reads the engine's
`-1.0` sentinel because `C_Player` overrides `GetPseudoSpeed` (WO-100 §10.3), so
recovering it means a virtual call added for no behaviour: pace and direction
come from the tags, which are the authoritative locomotion signal, and the
channel costs nothing without it. The sentinel is sent as 0.

The field stays on the wire because it is free and it is real on an ordinary
actor — which is where the puppet path will want it.

### 3.2 Item 6 — a recorded deviation

WO-100 §7 asked for correction magnitude and snap count "added to the existing
`GhostAgg` aggregation". `GhostAgg` lives in the **agent**, and the agent cannot
observe either number: it knows the packet positions but not where the ghost
body actually is, and **the gap between those two is the correction**. Putting a
number the agent cannot see into an agent-side aggregate would have meant
inventing it.

Both are therefore computed in `KCD2MP_InterpTick`, where the lerp happens, and
reported as `MP-GHOSTCORR ghost=… n=… corr_mean_m=… corr_max_m=… snaps=…`.
Stated as a deviation rather than presented as compliance.

### 3.3 What the receiver does, and does not, do

The remote body is driven from the peer's tags — the locomotion clip is chosen
from their real `pace`/`stance` instead of from our inferred packet speed —
behind `mp_anim_legacy_on|off`, defaulting to the new path and **fail-closed at
every step**: no body state, an unknown ordinal, or a posture the chooser
declines all fall back to the pre-0.23.1 inference for that sample.

Two limits stated rather than glossed:

* `dir` crosses the wire, resolves and logs, but this build's ghost clip set has
  no directional variants to select — there is no backward-walk tag to pick.
* **Nothing writes a Mannequin tag onto the remote body.** `AI.SetAnimationTag`
  and `Action.PersistantEntityTag` exist as method-name strings in
  `CryAISystem.dll` / `CryAction.dll`, but being a string is not being
  registered (WO-65: `pairs()` is blind to scriptbind methods, `type()` must
  probe live) and **the game was closed before this could be probed**. WO-101
  candidate.

## 4. Phase 3 — the discrete action channel

Implemented as WO-100 §6.2–§6.4 designed it, on `0x3B`/`0x3C`. 16 new tests,
all **(synthetic)**.

* One packet pair for every kind; the relay forwards the body verbatim and
  never interprets it, so a new action costs a payload.
* `phase` (press / commit / cancel / complete) is what makes this the input
  rather than the result.
* `gen` is the triple on the wire. One counter suffices locally because all
  three causes change the ghost's entity id; across the wire the receiver cannot
  observe the discontinuity, so the sender names it. **A new incarnation resets
  the ordering rather than rejecting it** — `seq` restarts with the body, and
  keeping the old `last-seq` would make every packet from the new body look
  stale. That is a test.
* Ordering per `(sender, kind)`, half-range modulo. The 16-bit wrap is tested
  explicitly: `0` must be newer than `65535`.
* The attack payload is wired from the `Requested*` properties, read over the
  pipe in the same round trip as the body state. **Sent whether or not Phase 1
  landed**: the receiver logs it and drops it as
  `dispatch=dropped-no-receiver`, which proves the wire half independently of
  the native write the engine refused.

**Honest limit.** The edge detector polls at 250 ms, and WO-100 §10.4 caught a
whole attack inside ~950 ms. A fast press-commit-release will sometimes read as
one edge. That is a property of polling, not of the channel; the fix is a native
edge hook, which is a behaviour change in the DLL and is not in this WO.

## 5. Phase 4 — the carry-ins

### 5.1 Airborne — closed, negatively, from shipped data

WO-100 §9 candidate 1 guessed "likely a scope context rather than the global
one". **The shipped data refutes the premise** (code-verified).

`kcd_pose_tags.xml` carries the `ActorState` group (`jump` `fall` `land` …).
Searching every file in `Animations.pak` for references to it, and to the two
tag files that import it:

| tag file | referenced by |
|---|---|
| `kcd_pose_tags.xml` | `kcd_combat_tags.xml`, `kcd_hitdeath_tags.xml`, and three `*_fragmentids.xml` |
| `kcd_combat_tags.xml` | ten `*_fragmentids.xml`, nothing else |
| `kcd_hitdeath_tags.xml` | thirteen `*_fragmentids.xml`, nothing else |

**Not one of them is referenced by a `<Tags>` element on any `ControllerDef`.**
A ControllerDef's `<Tags>` is the global tag definition — the live `TagState`
this project reads at `SAnimationContext + 0x10`. `<Fragments>` is a different
tree (`SControllerDef + 0x18`, WO-100 §1.2), and the tag definitions under it
are **fragment-selection tags**: matched when a fragment is queued, not held as
continuous state.

So there is no other tag context carrying a readable `jump`/`fall`/`land` bit.
Airborne is expressed by *which fragment is playing*, not by a tag. No live
probe is needed and no runbook is deferred — the question is answered.

Consequence: airborne stays inferred from the packet stream's vertical rate,
which is what `istate.isAirborne` already does (WO-38 Phase 3). That is now a
considered choice rather than a gap.

### 5.2 The `0x12`/`0x14` guid fallback — gated, and finally visible

Found on reading: the gate WO-100.5 asked for **already existed**. `0x12` fires
only when the name lookup returned nothing, or when the target is a `kcd2mp_`
ghost body — whose soul guid is the shared roster soul and therefore stable, so
that case is correct by construction and is now labelled `route=guid-ghost`
rather than lumped in with the hazard.

What was missing was not a gate but *visibility*: nothing in a field log
distinguished "this path fired and did nothing" from "this path never fired".
Both directions now print on the `MP-DMG` channel with `route=guid-fallback` and
a result of `applied` / `unresolved` / `disabled`, and `0x14` gets the same
treatment (`route=guid-fallback-death`).

Behind `--guid-damage-fallback` / `--no-guid-damage-fallback`, **default on** —
on is byte-identical to every previous release, and removing the path entirely
is the experiment, which has never been run.
