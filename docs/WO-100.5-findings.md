## 1. Phase 0 — `NPC_NAI`, and why it is not the answer

### 1.1 The live scoreboard

One session, one save, four probe bodies, all spawned with the same roster soul
guid (`ttkc_man_26`, the `KCD2MP.faceFallback` entry). The decisive measurement
is the engine's own line
`Skirmish event: HitTarget on Dude (target <name>)` — 20 of them in a
71,829-line log, counted across the whole file (**observed**):

| body | class | spawn | `HitTarget` |
|---|---|---|---|
| `wo1005_A_nai` | `NPC_NAI` | `System.SpawnEntity` | **0** |
| `wo1005_B_npc` | `NPC` | `System.SpawnEntity` | 2 |
| `wo1005_C_noai` | `NPC` | `XGenAI`, `NoAI=true` | **7** |
| `wo1005_E_ctrl` | `NPC` | `XGenAI` | 0 (never hit; it was the *witness*) |

The maintainer landed "a shitload of hits" on the `NPC_NAI` body across two
trials, one at night and one at 14:00. **The skirmish system booked none of
them.**

### 1.2 Item 1 — perception. The cost is bigger than the question

`bWH_PerceptibleObject` being absent is the headline, but it understates it. An
`NPC_NAI` body is not merely invisible to the perception system; it is outside
the combat bookkeeping. Hitting it produces exactly one thing — its own
`COMBAT_VICTIM_SCREAM_RECEIVED_HIT` dialogue, three log lines — and no
`HitTarget`, no witness, no crime, no guard (**observed**, twice).

Hitting the ordinary `NPC` beside it produced 37 lines: `SVEDEK_VIDI_JAK_NPC_
DOSTALO_ZASAH` (witness sees an NPC take a hit), `OBET_REPORTUJE_STRAZI_
(ASSAULT__UNARMED)` (victim reports to a guard), skirmish soul add/remove,
`alerted` tags, and guard `ttkc_man_23` running crime barks through to
`STRAZ_PATRA_NA_MISTE_CINU_A_ROZPOZNA_HRACE`.

**So with the class swap on, a ghost stops being a crime victim.** That
directly reverses WO-68's shipped behaviour ("ghosts join vanilla
crime/reputation"), which is far more than the WO's framing anticipated. It is
the reason the toggle defaults off.

### 1.3 Item 4 — the class swap does not survive the ghost path

Not a plumbing bug on our side. The engine substitutes the class
(**observed**, 3 of 3):

```
XGenAIModule.SpawnEntity{ClassName="NPC_NAI", ...}              -> built NPC
XGenAIModule.SpawnEntity{ClassName="NPC_NAI", NoAI=true, ...}   -> built NPC
System.SpawnEntity{class="NPC_NAI", ...}                        -> built NPC_NAI
```

And `System.SpawnEntity` is the path that does **not** bind `SharedSoulGuid`
(WO-22). So the two spawn APIs offer **the class or the soul, never both**.
Since WO-22, a soulless ghost is the A1 unconsciousness bug; the soul is not
optional. The class swap is therefore unreachable on the ghost path by
construction, and the primary spawn would silently ignore it.

`mp_ghost_nai` still ships, because the WO asked for it, but
`KCD2MP_SetGhostNai(true)` prints that finding every time it is switched on
rather than letting a toggle quietly do nothing.

### 1.4 `NoAI=true` — the lever the phase was actually after

`NoAI` is a shipped parameter of `XGenAIModule.SpawnEntity`, listed in
Warhorse's own scriptbind doc beside `Name` / `ClassName` / `SharedSoulGuid` /
`SchedulerProxyName` — the same doc WO-22 read the flat-table shape out of. It
keeps everything the class swap threw away and still removes the brain
(**observed**):

| | `NPC_NAI` | `NPC` + `NoAI=true` | `NPC` |
|---|---|---|---|
| entity class | `NPC_NAI` | `NPC` | `NPC` |
| soul binds (XGenAI path) | unreachable (§1.3) | **yes** | yes |
| `HitTarget` registrations | 0 | **7** | 2 |
| witnessed / reported as a crime | no | **yes** | yes |
| `SituationController` registrations | 0 | **0** | 3 |
| `npc_basic_scheduler` behaviour tree | 0 | **0** | present |
| self-initiated dialogue (gossip, greeting) | 0 | **0** | 7 |
| engine line when hit | scream only | `'<name>': no valid reaction found` | full reaction |

Ships as `mp_ghost_noai_on` / `mp_ghost_noai_off`, argless, **default off**.
Off is byte-identical to every previous session: the `NoAI` key is added to the
spawn table only when the toggle is on.

### 1.5 Item 2 — situations, and what it means for WO-99.5

Situation registration goes to **zero** for both `NPC_NAI` and `NoAI=true`
(**observed**). But WO-99.5's script-context crime fix is **not** made dead
weight, and the reason is §1.4's table: the body we will actually ship
(`NPC` + `NoAI`) is still a full crime participant — witnessed, reported,
guards dispatched. The script contexts are what stop a *ghost* being treated as
a townsman for crime purposes; `NoAI` removes its *initiative*, not its civic
standing. Two mechanisms, two jobs. Stated explicitly, as asked.

### 1.6 Item 3 — faction

No `does not have a faction` line from any of the four bodies (**observed**).
WO-100 §10.6's caveat is confirmed and bounded: the spam is a *bare* spawn
symptom, and a bound soul is sufficient to remove it. The ghost path already
binds one.

## 2. Phase 1 — the first combat write

### 2.1 Item 1 — the second call site, and two corrections

`0x76500` has **16 direct `E8` call sites** (code-verified, scanned over
`.text` with the `.pdata` function table for bounds). Three were read:

| site | what it pins |
|---|---|
| `0x1268C4` `C_CombatAutomationBlock::FireAction` | WO-100's original |
| `0x76CE5` | a 4-arg wrapper `(actor, out, int, byte)` that hardcodes `r8b=6` and `[rsp+0x28]=-1` and forwards the other two — this is what pins arg4 as the int and arg5 as the byte |
| `0x47E13` | `rcx` is the combat actor: the same basic block reads `[rcx+0x2F0]` (the model) and branches on `[model+0xA20]`/`[model+0x9E0]` to pick `r8b = 4` or `1` |

Confirmed signature:

```
void* RequestAction(I_CombatActor*, void** outAction,
                    uint8 actionTypeId, int32 zoneId,
                    uint8 handSlot, int32 param6)
```

**Correction 1.** WO-100 recorded the last two arguments as one
`int64 packed(strength, -1)`. They are two separate slots — a byte at
`[rsp+0x20]` and a DWORD at `[rsp+0x28]`.

**Correction 2, the one that mattered.** WO-100 handed over `0xF4C20` as "the
property setter, `(propertyBase, value, flag)`". **It is not a property setter**
(code-verified):

* 25 of its 26 direct call sites pass the *same* object, `model + 0xEE8`.
* Its body is `if (((uint8*)obj)[8 + index] == value) return;` — literally
  `cmp byte ptr [rbp + rsi + 8], dil` with `rbp = movsxd(edx)`. The second
  argument **indexes a byte array**.

Real signature: `SetFlag(void* flagsObj, int32 index, uint8 value)`, against a
flag-array object at `model + 0xEE8` with a vptr at `+0x00` and the bytes at
`+0x08`. Following WO-100's note would have written a byte at
`propBase + 8 + value` — the project's standing trap, in write form.

So the first write became the shipped call with the shipped arguments:
`C_CombatPlayerController::SetStandardGuardRequest` (`0x33F110`) does exactly
`SetFlag(model + 0xEE8, 0, 1)`.

### 2.2 Items 2 and 3 — the write. **LIVE-VERIFIED**

```
CW: model=0000025162161200 known-answer OK (model+0x200 names itself "RequestedAtkZone")
CW: prologue OK for SetFlag(0xF4C20) at CombatModule+0xF4C20 (15 bytes)
CW-SET: calling SetFlag(obj=00000251621620E8, index=0, value=1) -- flag[0] reads 0 before
CW-SET: flag[0] before=0 after=1 wanted=1 -- TOOK (read back at one byte, the correct width)
```

`obj == model + 0xEE8` exactly. Read back at **one byte**, which is the width
the trap in WO-100 §10.5 is about. No crash.

**The strongest single piece of evidence is one nobody asked for:** thirteen
seconds later, before the next command, `flag[0]` read `0` again. The game
*consumed* the write. That distinguishes "we changed a byte" from "we reached a
live system" and it is the check the WO's read-back alone would not have made.

### 2.3 Item 4 — the block action. **REFUSED, and the blocker is specific**

Fired on the player, in a real fight, prologue verified:

| `actionType` | `zone` | `hand` | result |
|---|---|---|---|
| 6 | 0,1,2,3,5 | 0 | null, every time |
| 6 | 1 | 1 | null |

Six calls, six nulls, no crash (**observed**). **The refusal is not the
arguments.**

And a correction to my own probe, caught by checking rather than assuming: the
line `"Automated block was not triggered - anim queue failed!"` is printed by
the shipped **caller** (`0x126800`), not by `0x76500`. A direct call cannot
produce it — zero occurrences in the whole 71,829-line log across all six
refused calls. The null return is the entire report. WO-100 §4.2's claim that
"the engine already reports this action's failure at this level" is wrong: it
reports it one level *up*, in code we are not running.

**Not tried: an NPC.** Every shipped call site fires on an AI-driven body, and
`C_Player` has already been caught overriding combat behaviour in this exact
area (WO-100 §10.3, `GetPseudoSpeed`). That is the obvious next step and it did
not happen because the fight ended. **WO-101 candidate, top of the list.**

Per item 6, no attack was attempted: block behaved unexpectedly, so the
sequence stopped there.
