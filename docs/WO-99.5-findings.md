## 1. Phase 0 — the `Dude` root cause

### 1.1 What was wrong

`g_player` was captured once during the RTTR walk (`rttr_abi.cpp`, `walk_to_soul`)
and never refreshed (**code-verified**). WO-99's account of the consequence was:
a save load rebuilds the player soul at a new address, so the `soul != g_player`
test in `sample_health` silently stops matching and the local player is reported
as an NPC named `Dude`. WO-99 fixed the symptom agent-side.

**That account is repeated here as WO-99's, not endorsed.** §1.4 tried to
reproduce the save-load trigger live and could not. The stale-pointer defect is
real; the trigger attributed to it is not established.

Second defect in the same function: the tracked set is rebuilt every 3 s with
`credit = 0`, so damage credited on a peer's behalf expired before the health
drop it was meant to cancel could be observed — the soul's `GetState(health)`
lags actor health by ~12 s, which is why WO-99 measured the echo at 12 s to
3 min rather than instantly.

### 1.2 What shipped

1. `g_player` is refreshed from `SoulList.PlayerSoul` on every rescan,
   keep-on-failure so a transient read never nulls a working pointer.
2. `g_combat` hangs off the same object and inherits the identical defect; it is
   re-read whenever the player soul moves.
3. `g_rpg` / `g_souls` are re-read too and log loudly if they ever move. This
   turns "SoulList looks stable across a load" from an inference into an
   observation either way.
4. `credit` is carried across the rebuild keyed by guid.
5. **`health` and `dead` are carried with it, deliberately.** Carrying `credit`
   alone would have been *worse than the bug*: the cancelling drop would still
   never be observed across a rescan, so the credit would go stale and silently
   cancel the next genuine local hit instead. They are carried only while the
   guid maps to the same soul pointer.
6. On a detected save load the carry is dropped whole — every pointer in the old
   set is dead, and credit owed in a world that no longer exists would cancel
   the first real hit in the new one.

### 1.3 Cached-pointer audit (the standing lesson applied)

Swept every file-scope and function-local static in the DLL. Only
`rttr_abi.cpp` caches engine object pointers at all.

| cached thing | save-load exposure |
|---|---|
| `g_player`, `g_combat` | **exposed** — both fixed. `g_combat` is only reached by `probe_take_damage`, a one-shot experiment, so its staleness was low-impact but identical in shape |
| `g_souls`, `g_rpg` | same exposure in principle; now re-read per rescan with a loud log on change. Confirmed live in §1.4: neither moved across three save loads |
| `Tracked::soul` | bounded to one 3 s window; health continuity now gated on the pointer being unchanged |
| `g_trampoline`, `g_original`, `g_importer` | code/module pointers — module lifetime, not exposed |
| `g_pipe` | OS handle — not exposed |
| `g_lastSeen*`, `g_isolationArmed`, `script_context`'s `names[][]` | plain storage — not exposed |
| `concept_read`'s static `CryStr` | not a cache; re-walks from `GameInterface` on every call |

**Residual, named rather than hidden:** for up to 3 s after a load the sampler
calls `GetState` on freed soul pointers. `call_invoke1` is SEH-guarded so that
survives, but SEH over *reused* heap returns garbage rather than faulting —
silent wrong data, not a crash. The rescan cadence was not changed.

### 1.4 Live result — the trigger condition did NOT reproduce

Run live, with the maintainer at the keyboard. **Three within-process save
loads**, one of which changed the world substantially (tracked soul count
7 → 33), across two processes:

| | |
|---|---|
| process | pid 2112 unchanged across all three loads |
| `PlayerSoul` at walk time | `000001E02C0B5F20` |
| `g_player` after three loads | `000001E02C0B5F20` — **identical** |
| `soul+0x40` WUID | `0x0500000000000251` — intact (and the same value in a *different* process earlier, so it is an entity id, not an address) |
| control `HasEntityContext("UnconsciousHolsterInsteadDropWeapons")` | **true** |
| negative control `kcdmp_wo68_not_a_context` | **null** |
| `npc=Dude` at the native layer | **none** (observed) |

The pointer is **live and valid**, not stale — a freed object could not pass
those controls. So no `PlayerSoul moved` line is the *correct* output here.

**Consequence, stated plainly: a save load does not rebuild the player soul on
this build.** WO-99's account of the root cause was "a save load rebuilds the
player soul at a new address"; that mechanism **did not reproduce** in three
controlled trials.

What survives and what does not:

* **Survives (code-verified):** `g_player` genuinely was captured once and never
  refreshed. The defect is real and the fix is correct-by-construction.
* **Does not survive (observed):** the attribution of the `Dude` bug to a save
  load. WO-99's "both machines had reloaded before their first `Dude` line" is
  now correlation with no demonstrated mechanism.

**Alternative hypothesis for the next session**, which fits the same evidence and
which this fix does *not* address: if the player's entry in `SoulsByGuid` is a
different object from `SoulList.PlayerSoul`, then `soul != g_player` is true for
the player on **every** pass with no reload involved at all. Cheaply testable
with a read-only map probe comparing the two.

### 1.5 Instrumentation fixed as a result

The refresh logged only on change, so "no line" was ambiguous between "ran and
found nothing to do" and "never ran" — the identical silent-guard shape this WO
exists to stamp out. It now reports the first check of each session and one per
~5 min thereafter, including when the read fails, so the field session can tell
those apart without a debugger.

## 2. Phase 1 — step 0, and two corrections to WO-97

### 2.1 The probe

`C_Node::GetPort` is **exported** (ordinal 199) and its signature came from the
export table rather than inference (code-verified):

```
?GetPort@C_Node@conceptmodule@wh@@QEBA?AV?$_smart_ptr@VI_Port@...@@AEBV?$CryStringT@D@@@Z
public: _smart_ptr<I_Port> __cdecl C_Node::GetPort(CryStringT<char> const&) const
```

`QEBA`, not `UEBA` — a **non-virtual** public member, so the exported address is
the real implementation. That matters because the exported `I_Port::Read`
(`0x2B1CF0`) and `I_Port::Trigger` (`0x2B1DB0`) are the empty base virtuals.
Both are resolved in the probe, never called, and used only as comparands.

Step 0 answers "which function will actually run" two independent ways: the vptr
against `C_ActiveTriggerPort::vftable`, as WO-97 §4.4 specified, and every vtable
slot resolved against ConceptModule's exported symbols by address. The second is
stronger — two comparands are exported by name, so the empty-base rejection is
anchored on a symbol rather than an RVA.

`ConceptModule.dll` sha256 = `AB4032AC0410E907…`, **matching WO-97's
`ab4032ac…`** (observed), so every WO-97 RVA applies to this exact binary. The
hard-coded vftable RVA self-check passed: `vftable+0x78` == `C_ActiveTriggerPort::Trigger`.

### 2.2 The results (observed, live)

### 2.3 Correction 1 — WO-97 §3.5's class table is wrong

WO-97: "of the 17 genuine `I_Port` subclasses, only **two** have a real slot 15."
Enumerated every port class by RTTI out of `ConceptModule.dll` and read each
one's actual slot 15 (code-verified):

| class | slot 15 | slot 16 |
|---|---|---|
| `C_ActiveTriggerPort` | **real** | empty |
| `C_InterfaceTriggerPort` | **real** (same fn) | empty |
| `C_OutputTriggerPort` | **real** (same fn) | empty |
| `C_StaticTriggerPort` | **real** (same fn) | empty |
| `C_AutoTriggerPort`, `C_InputTriggerPort` | own override `0xCC580` | empty |
| `C_DebuggerPort` | own real | concrete |
| `C_TriggerPort`, `C_EdgePort`, `I_Port` | **empty base** | empty |
| 9 data/constant/asset ports | empty base | **concrete** |
| `C_PortRef` | forwarder | concrete |

**Six** classes have a real or own slot 15, not two.

### 2.4 Correction 2 — the direction model is incomplete

WO-97 code-verified `PortDef::InTrigger` → 1 and `OutTrigger` → 2. T1 returns
**3**. A bitmask (In|Out) fits, but that is an inference and is **(inconclusive)**.

### 2.5 Why nothing was fired, and what it means for WO-100

- T1 carries the genuinely real `Trigger`, but the two step-0 checks disagree,
  and `IsEmpty()` is **true**. `C_ActiveTriggerPort::Trigger` propagates by
  walking the port's outgoing connections; an empty port plausibly has none. The
  path contains `hibernable` and the branch may not be live at this save point.
- T2 has direction 1 and `IsEmpty()` false — WO-97's stated preconditions — but
  its slot 15 is a **third** implementation WO-97 never found. Checked whether it
  propagates: the control function self-identifies as `C_ActiveTriggerPort::Trigger`
  from its own `__FUNCTION__` string, while `0xCC580` carries no `::Trigger`
  string and is a real function doing a guarded virtual dispatch through slot 22,
  referencing `Direction`. Whether it propagates a trigger is **(inconclusive)**.

Firing either would have been precisely the unfalsifiable call WO-97 warned
about. **The gate refused; that is the gate working.**

**WO-100 does not become the quest write layer on this evidence.**

## 3. Phase 2 — blocked, with the reason and the retarget

**Every trigger-port class inherits the empty `I_Port::Read`** (§2.3,
code-verified; confirmed live on both targets). The sacks known-answer read can
therefore *never* come from a trigger port — the probe refused for exactly the
reason WO-96 §7 warned about: calling the empty base would have returned an
empty variant and presented as "works, objective is none."

The nine data/constant/asset port classes do have concrete `Read`s. The read has
to target the objective's **data** port — per WO-96 §3.3 the objective state
lives at `…/_objectiveVisualNN/Logs/<State>`, a different node from the trigger
node. Naming and probing that node is the retarget; not reached this session.

The `Read` machinery itself is implemented and shipped, gated so it refuses the
empty base rather than producing a false negative.

## 6. Environment notes

### 6.1 The AppData redirect bit again, and `ModuleMemorySize` is the answer

The deployed `KCDMP.dll` reads from this shell as 299,008 bytes / sha256
`366F5BE0…`, which matches **nothing that was ever built**. That is the WO-74
sandbox redirect showing a phantom file. The authoritative check is the *loaded
module*: `ModuleMemorySize == SizeOfImage` (380,928) — read from the process,
not the filesystem. Same for `agent.log`; `kcd.log` and the native mirror log
(both in the game root on D:) are reliable and were used throughout.

### 6.2 A GPU crash that was not ours

At 14:44:28 the game died with `DXGI_ERROR_DEVICE_REMOVED` (fatal error 242),
~2 minutes after the new DLL was first deployed. The new DLL was the prime
suspect and was investigated as such. It is exonerated on evidence:

- the crash log contains **408** `[CCommandListFenceSet] WaitForFence(CPU) TIMED OUT`
  lines, the GPU fence stuck at 58747 while the CPU waited for 58751
- the mod's own `tickstat` reported `max=82070.0ms`, an 82-second tick
- the native sampler's `SAMPLE` lines stop at 14:42:26 and resume at 14:43:49 —
  an 83-second gap corroborating the same stall independently

The main thread was **parked in a D3D12 fence wait**, which is *why* the 3 s
sampler produced nothing: the main-thread pump was blocked by the renderer, not
blocking it. The mod reported the stall; it did not cause it. Crash log preserved.
