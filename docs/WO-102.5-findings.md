Evidence marks, strict: **(observed)** = a log or a screen; **(code-verified)**
= read out of source, a binary or a shipped data file; **(synthetic)** = a

## 1. Phase 1 — pause on by default, and guarantee resume

### 1.1 Shipped: `mp_authority_pause_on|off` now ships **on**

`KCD2MP.wo102.authorityPause = true`. Evidence behind it is unchanged from
WO-102 §3.3's solo probe (8/8 runs: `verdict_pos=HELD`, animation continues,
hits register, clean resume across `ttkc_man_2`/`ttkc_man_6`/
`ttkc_woman_10`) — **still (observed) solo, single NPCs, never under a live
two-machine puppet stream.** That caveat is stated in the toggle's own
comment in `kdcmp.lua`, not just here, so it travels with the code.

### 1.2 Resume guarantees added this session (code-verified; synthetic,
scenario `aa`, 9 new checks)

WO-102 §4.2 already resumed on three paths: puppet release for silence,
`mp_authority_pause_off`, `mp_authority_host_off`. Added:

* **`KCD2MP_Stop()`** (reached today only by the `mp_stop` console command;
  no other live path reaches it) now resumes everything still paused before
  `KCD2MP_RemoveAllGhosts()` runs.
* **The agent going away** — closed, crashed, or the relay dropped it. The
  game and its Lua state keep running without the agent, so `KCD2MP_Stop`
  is never reached from that side. New global `KCD2MP_Wo102ResumeAll(why)`
  wraps the existing local `mp_wo102_resume_all`; `GameBridge.cs`'s existing
  disconnect path (the one that already calls `KCD2MP_RemoveAllGhosts()`)
  now also calls this.
* **A periodic reconciliation sweep** (`mp_wo102_reconcile_pauses`, every 5 s,
  hooked into `KCD2MP_NpcSyncTick` — which runs on every client regardless of
  `npcSync.enabled` or authority role, unlike the puppet tick, which stops
  entirely when there are no puppets). Resumes any name in
  `KCD2MP._npcPaused` with no entry in `KCD2MP.npcPuppets` — the catch-all
  for **peer disconnect** and any other way a puppet stops existing without
  going through the normal release call. A bespoke immediate
  resume-on-ghost-removal hook was considered and NOT built: it would need to
  match `KCD2MP.npcPuppets[name].owner` (a raw value from the agent, numeric)
  against a ghost id from `KCD2MP_RemoveGhost` (whose type was not pinned down
  this session), and a wrong-type comparison that silently never matches is a
  worse failure mode than the sweep's ≤5 s exposure window. Peer disconnect
  is additionally already covered within ~3 s by the existing silence-release
  path (a disconnected peer's stream goes silent, which already calls
  `mp_wo102_resume(name, "silence")`) — the sweep is the net under that, not
  the only thing catching it.
* **`MP-SUMMARY-MOD`** gained `auth_paused_now=` — the count of names
  currently in `KCD2MP._npcPaused` at summary time, so a bundle audit can
  compare it against `auth_pauses - auth_resumes` (they should agree; a gap
  means some pause was lost track of without a matching resume log line).

### 1.3 The save-persistence question — narrowed, not closed

Searched (code-verified, string scan, `XGenAIModule.dll`): **`wh::xgenaimodule::C_IntelligentObject::Save` exists** (alongside `::Suspend`/`::Resume`,
the functions WO-102 §3.5 already decompiled). This is the one piece of new
evidence this session found — a Save-named method on the exact class that
holds the pause/suspend bitmask (`obj+0x128/0x129`). Whether it touches that
mask is what would answer the question, and that needs a decompile this
session did not complete in time (see below).

**No engine hook exists to resume-before-save either way** — searched
alongside the pause lever itself (WO-102 §3) and not found again this
session; a Lua-side "resume everything right before a save" is not
buildable without one. So the periodic reconciliation sweep (§1.2) is the
actual mitigation regardless of the answer: it bounds exposure to ≤5 s
between a puppet disappearing and its pause being lifted, which bounds how
often a save can land on a genuinely-still-paused NPC even if the engine
does serialize the state.

### 1.3.1 Addendum, same day (code-verified, Ghidra 12.1.3 on `XGenAIModule.dll`,
finished after §1.3 above was written) — **the question is narrowed, not
still wide open**

The 51 MB import that WO-102 §3 could not finish in its own session (and
that this session started in the background before Phase 1 closed) landed.
`wh::xgenaimodule::C_IntelligentObject::Save` (`0x181092e40`, 3,414 bytes)
was decompiled:

```c
if ((*(byte *)(param_3 + 0x10) & 0x40) != 0) {
    ...
    pCVar6 = wh::framework::C_OutputChunk::CreateChildChunk(param_2,0xdae,bVar1);
    ...
    local_198[0] = *(undefined1 *)(param_1 + 0x128);
    wh::framework::C_OutputChunk::WriteBytes(pCVar6,local_198,1);
    wh::framework::C_OutputChunk::DestroyChildChunk(param_2);
}
```

`param_1 + 0x128` is the exact byte WO-102 §3.5 already identified as the
`C_IntelligentObject`'s own three-valued suspend/context state — the SAME
field `Suspend`/`Resume` (`0x1612290` in that findings section) read and
wrote. **This function writes it into a real save chunk** (`C_OutputChunk`,
chunk id `0xdae`, `WriteBytes`) — not a debug dump, the actual serialization
path a class's `Save` method feeds. This is unambiguous: **the pause state
CAN be written into a savegame.**

What is still open, narrower than before: the write is conditional on a
flag byte (`param_3+0x10` bit `0x40`) whose meaning was not traced this
session — it could be "this is a full save" vs. a lighter checkpoint, or
something else. Bit `0x10` gates a different child chunk (`0xdac`) just
below it in the same function, so this class's `Save` clearly makes several
independent, flag-gated choices about what to include. No matching
`C_IntelligentObject::Load`/`Restore`/`Read`-named method was found by
string search (the read side may be a generic chunk-id dispatch elsewhere,
not a per-class named method) — so whether a restored suspend byte
actually re-applies the pause on load, or is read and then ignored, is
**still (inconclusive)**.

**Revised verdict: the state IS captured in at least one save-chunk write
path (code-verified) — no longer merely suspected. Whether that write
fires on an ordinary quicksave, and whether the restore side re-applies it,
remain (inconclusive)** and are exactly what runbook item 1 below settles
live. The reconciliation sweep's ≤5 s bound is now demonstrably mitigating
a real write path, not a hypothetical one.

## 2. Phase 2 — the native NPC scan

### 2.1 What was searched, and what it found (code-verified, Ghidra 12.1.3,
this session)

Reused the WO-102 §1.2 discipline: decompile the real Lua-binding handler
rather than assume a generic CryEngine layout (a generic SDK's `gEnv`/vtable
layout is NOT trusted here — this build's own binaries are the only source).

* **`gEnv` is not exported by name in this build.** Checked `CrySystem.dll`,
  `CryEntitySystem.dll`, `CryScriptSystem.dll` for `gEnv` /
  `SSystemGlobalEnvironment` export strings — none. Every CryEngine DLL keeps
  its own private static `SSystemGlobalEnvironment*`; `KCDMP.dll` has none of
  its own (it is not a CryEngine module), so it reads a HOST DLL's copy out
  of that DLL's data section.
* **`CScriptBind_System::GetEntitiesInSphere`** (`CryScriptSystem.dll`,
  handler `FUN_1800279e0`, found via the registered string
  `"GetEntitiesInSphere"` in the registration function `FUN_180022ea0`,
  exactly the WO-42/WO-102 anchor-string technique): reads
  `*(SSystemGlobalEnvironment**)(imageBase+0x8E560)`, then `+0xA0` for
  `pEntitySystem`. **This call walks `IEntitySystem`'s FULL entity iterator
  every time, unconditionally** — `GetEntityIterator()` (vtbl+0xB0),
  `MoveFirst()` (vtbl+0x30), `Next()` (vtbl+0x20) in a loop, computing squared
  distance per entity itself. It is NOT a spatially-scoped query. This is the
  real cost model behind the WO's premise: Lua's `mp_npc_rescan` pays this
  walk once per anchor, every scan tick, plus a script-table construction for
  every entity that matches.
* **`CScriptBind_System::GetEntitiesInSphereByClass`** (`FUN_180027c40`, same
  registration function): the SAME `pEntitySystem` object, two MORE vtable
  calls — `GetClassRegistry()` (vtbl+0x58) and, on the registry,
  `FindClass(const char*)` (vtbl+0x18) — and, per entity, `IEntity::GetClass()`
  (vtbl+0x18, a *different* vtable, same slot number by coincidence) compared
  by pointer against the resolved class. Two independent vtable calls on the
  same `pEntitySystem` both matching `IEntitySystem`'s documented interface
  shape is the cross-validation this build offers without a live process to
  call it — not proof, but not a guess either.
* **`CScriptBind_Entity::GetName`** (`CryEntitySystem.dll`, handler
  `FUN_18000ebe0`, found via the registered string `"GetName"` in the
  `CScriptBind_Entity` registration function `FUN_180006500`, the same
  function WO-102 §1.2 already used for `GetWorldPos`/`SetWorldPos`): reads
  `entity+0xE0` directly (`plVar2[0x1c]`, no vtable call) and hands it to a
  string-wrapping helper as a plain pointer — a `CryStringT`'s exposed data
  pointer. WO-97's negative-refCount trap means this is read defensively
  (length-capped, printable-ASCII-gated, never trusted blind).
* **Position/yaw**: the SAME `CEntity::m_worldTM` offsets WO-102 §1.2
  established (`+0x58` Matrix34, position at `+0x64/+0x74/+0x84`) — this is
  the same `CEntity` class, so the same offsets apply to any entity, not only
  the player's. Re-derived in `npc_scan.cpp` rather than shared via a header
  with `local_state.cpp`, to avoid touching that file.

### 2.2 What was built (code-verified; synthetic 125/125 incl. 16 new in
`tools/Test-WO102Synthetic.ps1`; agent 156/156 incl. 6 new)

* **`native/KCDMP/npc_scan.{h,cpp}`**: `kcdmp::npcscan::scan(anchors[],
  anchorCount, radius, &out)`. Gated exactly like `local_state.cpp`: the
  `gEnv`/`pEntitySystem` candidate is trusted only after the entities it
  hands back start passing `vptr == CEntity::vftable` (the same gate,
  reusing `CryEntitySystem.dll`'s `kRvaCEntityVftable`); zero matches among
  the first entities refuses the whole scan (`kGEnvUnmapped`) rather than
  returning a plausible-looking empty or wrong answer. The class registry
  resolution (`NPC`/`NPC_Female`/`Horse` → `IEntityClass*`) is cached for the
  process lifetime once it succeeds once — these are load-time singletons,
  not per-world state (unlike WO-99.5 §1.3's caution about cached
  actor/entity pointers, which this file does NOT do: `gEnv`/`pEntitySystem`
  are re-read fresh every call). Per entity: class-pointer compare (no string
  compare), radius-to-nearest-anchor check, then the name read, all
  SEH-isolated. Byte-budgeted (`kMaxReplyBytes = 8000`); over budget sets
  `truncated=true` and stops rather than growing unbounded.
* **Pipe `0x0B ScanNpcs → 0x87 NpcScanResult`** (`pipe_server.h/.cpp`):
  request `[anchorCount:1][radius:4f][anchor×N: x,y,z]`, anchorCount 1..8.
  Reply is variable-length (14-byte header + `count` entries, each
  `nameLen+17` bytes) — this does NOT go through `send_frame`'s fixed
  1024-byte stack buffer (a scan reply can run past that); a dedicated
  `send_npc_scan_result` builds and writes it directly under the same write
  lock every other reply uses.
* **Agent (`dotnet/KcdMp.Client`)**: `NpcScanCodec` (decode), `CombatPipe.
  ScanNpcsAsync` (encode+round-trip, same give-up/refuse-code discipline as
  `ReadLocalStateAsync`), `GameBridge.NpcScanTickAsync` — its own 2 s cadence
  (independent of the position tick), anchors = own position + every peer
  ghost whose last-known position is fresher than 5 s (a stale anchor would
  scan around a body that has since moved). **Only the candidate NAME list is
  pushed to Lua**, as one `KCD2MP_ApplyNativeScan("name1,name2,...")` call —
  not position/yaw/class. Position/hp/dead/ko/drawn/engaged are re-read fresh
  per name in the mod's EXISTING `KCD2MP_NpcSyncTick` loop exactly as today
  (`System.GetEntityByName(name):GetWorldPos()` etc.), so the push stays
  small (a handful to a few dozen short strings) regardless of how many NPCs
  are in radius — this is what keeps the design safe against
  `HttpGameTransport`'s `MaxBatchChars` auto-chunking batching (4000 chars,
  code-verified `HttpGameTransport.cs`) ever mattering here. Give-up after 20
  consecutive refusals, same shape as `pos_native`'s.
* **Lua (`kdcmp.lua`)**: `KCD2MP.wo102.npcScanNative` (new field on the
  EXISTING WO-102 toggle table — this is a continuation of that toggle set,
  not a parallel system), `mp_npc_scan_native_on|off` console commands
  (argless, WO-94 discipline), agent push-at-connect
  (`KCD2MP_Wo102Set("npc_scan_native", ..., "agent")`), console mirror in
  `GameBridge.cs`'s `wo102_toggle` handler. `KCD2MP_ApplyNativeScan(csv)`
  parses the pushed names (re-gated to `^[%w_]+$`, the SAME pattern
  `mp_npc_rescan` already enforces — belt and suspenders, not a new rule) into
  `KCD2MP._nativeScan = { at, names }`. `mp_npc_rescan` is changed in exactly
  one place: **how `ents` is populated.** When `npcScanNative` is on and the
  push is fresh (age ≤ 3× `npcSync.scanMs`, i.e. 6 s at the 2 s default),
  `ents` is resolved from `KCD2MP._nativeScan.names` via
  `System.GetEntityByName`; otherwise (toggle off, stale, or never received)
  it walks `System.GetEntitiesInSphere` per anchor exactly as before, logging
  `MP-NPCSCAN dir=consume verdict=fallback reason=stale|never-received`.
  **Everything after that line is untouched** — mod-entity/mounted-horse/
  puppet exclusion, the `^[%w_]+$` name gate, distance-to-nearest-anchor
  ranking, the cap, the tracked-set diff, the acquire/release logging. A
  native candidate list is a speed change, not a behaviour change, by
  construction (same downstream code, different `ents` source).
* **Known-answer check**: `mp_npc_scan_compare` (console command, argless)
  runs a fresh Lua `GetEntitiesInSphere` enumerate over the SAME anchors and
  radius `mp_npc_rescan` would use right now, and diffs it against
  `KCD2MP._nativeScan.names` (the native scan's last push), logging
  `MP-NPCSCAN dir=compare lua_n= native_n= both= only_lua= only_native=` plus
  the two name lists. **`only_native` names are expected**: native does not
  replicate Lua's mod-entity/mounted-horse/name-pattern exclusion (by
  design — that filtering stays Lua-side per "policy stays in Lua"), so a
  ghost body or an excluded name can legitimately appear only on the native
  side. **`only_lua` names are the interesting failure** — every one means
  the native scan missed something the Lua walk finds, which is exactly what
  this check exists to catch. NOT run live this session (synthetic scenario
  `z` in `Test-WO102Synthetic.lua` exercises the parsing/consume/fallback/
  compare logic against fabricated data, not the real engine).

### 2.3 The measurement — NOT DONE. Runbook for the maintainer

Same shape as WO-102 §1.4: nothing here ran against a live game.

1. Build (`cmake --build native/build --target KCDMP`) and inject the
   build-directory DLL; verify `ModuleMemorySize` on the loaded module.
2. `mp_npc_scan_native_off` (default). Walk a village for ≥2 minutes.
3. `mp_npc_scan_native_on`. Expect in `kcdmp-native.mirror.log`:
   `NPCSCAN: class registry resolved NPC=... NPC_Female=... Horse=...` then
   `NPCSCAN: first scan OK total=... vptrOk=... matched=...`. In `kcd.log`
   expect `MP-NPCSCAN dir=consume verdict=native pushed=... resolved=...`
   every ~2 s.
4. **The known-answer check**: `mp_npc_scan_compare`. `only_lua` must be
   empty (or explain every name in it) for the native scan to be trusted at
   all — this is the pass/fail gate the toggle's default depends on, same as
   WO-102's oracle check was for position.
5. **The cost comparison**: this WO did not add per-path cadence
   instrumentation the way WO-102's `MP-POSCADENCE` did (no equivalent
   `MP-NPCSCANCADENCE` — out of scope this session, a real gap). What exists:
   `MP-NPCSCAN dir=native ... dur_ms=` per native scan (the pipe round trip)
   and the Lua `mp_npc_rescan` call itself is not separately timed. A future
   session should add a `os.clock()` bracket around the
   `System.GetEntitiesInSphere` branch and compare `dur_ms` distributions
   directly, the same way WO-102 compared `MP-POSCADENCE path=log|native`.
6. The decision: native earns its default only if `mp_npc_scan_compare`
   shows `only_lua` empty across a real session AND the native path is
   measurably cheaper. Neither has run. Default stays off.

## 3. Phase 3 — uncapped co-located ownership

### 3.1 What was built (code-verified; synthetic, scenario `bb`, 17 new checks)

* **The cap is removed under host authority.** `mp_npc_rescan`'s
  `cap = maxTracked * #anchors` becomes `cap = math.huge` when
  `authorityHost and hitSensorOn`. The claim model
  (`mp_authority_host_off`) is untouched — same `npcSync.maxTracked`, same
  per-anchor cap, byte-for-byte, proven by scenario `bb`'s own control case.
* **The radius is a separate, runtime-adjustable parameter under host
  authority**: `KCD2MP.wo1025.authorityRadius`, default 45 m (today's
  `radius * NPC_TRACK_EXIT_FACTOR` value — the conservative starting point,
  not an assumption of what 150 m costs). `npcSync.radius` (30 m) still
  governs the claim model exactly as before; the two radii are independent
  by construction, so flipping `authorityHost` off returns the OLD number,
  not just the old cap logic.
* **`#KCD2MP_SetAuthorityRadius("<metres>")`** — deliberately NOT a
  registered console command. WO-94: the console drops arguments from
  Lua-registered commands, and a bare `mp_x_on`/`_off` pair cannot carry a
  number. The `#<lua>` console syntax (evaluates the line as Lua directly)
  is the intended and only supported way to call this, exactly as the
  prompt itself specifies the invocation. Clamped to 10–300 m and rejects
  non-numeric input (including NaN) rather than silently taking a wrong
  value — a runaway radius is a runaway scan cost.
* **The agent's own copy of the radius stays in sync.** The native scan
  (Phase 2) runs agent-side and cannot read `KCD2MP.wo1025` — a radius
  change with no announcement would silently cap the native path at
  whatever the agent last knew, defeating the point of a larger radius
  whenever `mp_npc_scan_native_on` is also set. Fixed: `KCD2MP_SetAuthorityRadius`
  emits `KCD2MP_EmitEvent("authority_radius", "<m>")`; `GameBridge.cs` mirrors
  it into `_npcScanRadiusM` (a new mutable field, was a hardcoded const).
  Lua's own fallback path (`System.GetEntitiesInSphere`) needs no mirror —
  it reads `KCD2MP.wo1025.authorityRadius` directly every rescan.
* **Culling** (`KCD2MP.wo1025.npcCull`, default on, `mp_npc_cull_on|off`):
  an owned NPC beyond `cullRadius` (default 30 m) of every anchor is tracked
  (nobody else can claim it) but `KCD2MP_NpcSyncTick` skips its
  `KCD2MP_EmitEvent` call — the network cost a larger `authorityRadius`
  would otherwise add for NPCs nobody is near. An **engaged** NPC (fighting
  a player) is never culled **by construction**, not a special case:
  `NPC_ENGAGE_RANGE_SQ` is 12 m, always inside `cullRadius`, so "in combat
  with a player" and "within cull range" cannot diverge.
* **Re-entry is never a stale resume.** The tracked entry's `t.lastX/Y/Z/Hp/...`
  fields are deliberately left untouched while culled (the emit code returns
  before reaching them). The tick after re-entry therefore reads the
  position/hp/dead/ko/drawn state it ALWAYS reads fresh every tick (culled
  or not) against those stale `t.last*` values, so `moved` (or `hpChanged`,
  etc.) is true and it sends immediately — at the entity's current state,
  not a cached pre-cull one. No resync-flag machinery was needed for this;
  Phase 6's `NpcStateFlagResync` stays exactly what it was (a sleep/reload/
  fast-travel burst), not repurposed for culling.

### 3.2 The named risk — an NPC that acts while unobserved (decided)

**Position and life state (hp/dead/ko/drawn/engaged) are covered by §3.1's
re-entry behaviour** — they are read fresh the moment streaming resumes, so
nothing stale ever reaches a receiver. **Not covered, and not new to this
phase**: any detail that was never part of the state bitset in the first
place — a swing mid-animation exactly at the reveal moment, for instance.
WO-40's swing cue is already best-effort (`playerHit` + `drawn` + proximity,
not a combat log), for every NPC, culled or not; Phase 3 does not make this
worse, it just makes it possible for more NPCs to be in the "was not being
watched" state before a reveal.

**Quest NPCs and NPCs carrying synced state do NOT get a special
always-stream exemption this session** — decided, not deferred by accident.
No cheap, already-available signal exists in this codebase for "is this NPC
quest-relevant" (WO-90/94/96's quest layer tracks quest PROGRESS, not a
per-entity flag `mp_npc_rescan` could check without building new
infrastructure). A quest-critical NPC that both players are far from goes
quiet like any other under culling; the existing Phase 6 resync triggers
(sleep/wait/reload/fast-travel/new-peer/`mp_resync_npcs`) are what
re-converges it, same as they always were — culling changes nothing about
when those fire.

### 3.3 The 150 m question — not earned, and said so

The maintainer's target is 150 m; the shipped default stays 45 m.
`authorityRadius` alone controls the AREA scanned (≈70,000 m² at 150 m vs
≈6,400 m² at 45 m, about eleven times), `cullRadius` alone controls how much
of that area is actively STREAMED at any moment — the two are why culling
is what makes a large radius affordable at all, not a nice-to-have next to
it. Neither has been measured this session (no game ran). §5's radius
runbook is the actual answer; nothing here should be read as "150 works."

### 3.4 Wire compatibility (Phase 3)

No wire change. The cap/radius/cull decisions are entirely local to the
authority's own scan and emission gating — what crosses the wire is still
ordinary `npc_state` packets, fewer of them when culling is on, not a
different shape.

## 4. Phase 4 — co-location gating and the transition

### 4.1 What was built (code-verified; synthetic, scenario `cc`, 19 new checks)

* **One coarse state, not per-NPC**: `KCD2MP.wo1025.together` (bool),
  computed from the distance to the NEAREST peer ghost only — deliberately
  unlike the WO-60 claim model's per-entity claiming, which WO-102 §2.1
  showed produced 52 of 52 grants to one player and expiries mid-fight. A
  single, rarely-changing, session-level state is a different and much safer
  shape, and is now stated as such in the code, not just here.
* **Hysteresis + dwell**: `togetherEnterM=60`, `togetherExitM=90`,
  `togetherDwellS=10` (all in `KCD2MP.wo1025`, not yet exposed as their own
  console setters — a gap, see §4.5). Must close to ≤60 m to become
  "together", must open past 90 m to become "apart" again, each SUSTAINED
  for 10 s before the transition commits — `KCD2MP._togetherWantSince`
  tracks how long the opposite state has been wanted, and resets the moment
  it stops being wanted (a momentary crossing costs nothing). Proven
  synthetically: a 1-tick dip inside the enter band does not flip it; a
  sustained one does, at exactly the dwell boundary.
* **What the state actually gates**: `mp_npc_rescan`'s peer-ghost anchors
  are only added while `together`. The authority's OWN anchor is always
  scanned regardless — this is deliberate and is what makes departure
  handoff need no special-case code (§4.4). Going apart does not reach
  across the wire to tell a puppeting peer to let go; untracking on the
  authority side simply stops emission for that name, and the EXISTING
  silence-release path (WO-32/WO-90, ≤3 s of no packets) already resumes the
  pause and drops the puppet on the other side. No new wire message, no
  resync-flag repurposing — the same "reuse what already exists" pattern as
  Phase 3's re-entry behaviour.
* **Never mid-interaction**: an NPC this machine is fighting
  (`t.sentEngaged`, the same flag Phase 3's cull exemption already reads) or
  that is in dialogue (`e.human:IsInDialog()`, the same per-entity check
  `KCD2MP_ApplyNpcState`'s resync path already uses) is left tracked and
  marked in `KCD2MP._colocatePendingRelease` instead of being released by
  the transition. `KCD2MP_NpcSyncTick`'s own per-NPC loop sweeps it the
  moment neither is true any more — checked every tick, not just at the next
  transition, so a fight that outlasts the "apart" decision by any amount of
  time still gets released the instant it ends. Both counted and logged by
  the transition itself (`frozen=` vs `released=`), never silently dropped.
* **Departure handoff**: no NPC-sync-specific code was needed. The relay's
  existing Rule 2 reassignment (`BroadcastCombatRole`, already fired on
  every disconnect) flips `KCD2MP.hitSensorOn` on the surviving client via
  the agent; `KCD2MP_SetHitSensor` now resets `together`/`_togetherWantSince`/
  `_colocatePendingRelease` to a fresh state on becoming the NEW authority,
  and the survivor's own anchor is scanned unconditionally — it starts
  owning what is near itself on the very next rescan, no handoff-specific
  code. "With nobody remaining, do nothing" already held: a lone client
  scans only its own anchor either way.
* **The ungraceful case — a real gap, closed**: found, not assumed. The
  relay's per-client read loop had NO timeout — a silently dead peer (cable
  pulled, hard crash, no FIN, no RST) left the read parked forever, so Rule 2
  never reassigned. `ClientSession`'s main per-packet-header read is now
  wrapped in an explicit `CancellationTokenSource` (`Tcp:IdleTimeoutMs`,
  default 30 s — `NetworkStream.ReadTimeout` was tried first and **does not
  reliably apply to `ReadAsync`**, confirmed empirically this session when
  the first implementation attempt did not time out at all); a timeout is
  converted to the same `IOException` `RunAsync`'s existing catch already
  treats as a normal disconnect, so the SAME `BroadcastCombatRole`/
  `HandleDisconnect` cleanup runs. 30 s is 15× the real client's own 2 s
  position heartbeat (`GameBridge.cs`'s `PositionHeartbeatInterval`, which
  keeps running independent of the game's own `Script.SetTimer` chains, so
  it does not go quiet at a menu or loading screen).
* **This is the one piece of Phase 4 that is not merely synthetic** — 
  `KcdMp.Relay.Tests.IdleTimeoutTests` runs a REAL relay and two REAL TCP
  peers: peer alpha (the initial authority, Rule 2's lowest id) goes silent
  with no FIN, no RST, nothing; peer bravo pings every 100 ms to stay alive
  on its own; after the idle timeout the test asserts bravo actually
  receives a fresh `CombatRole` packet naming itself the new authority. This
  is a relay round-trip proof of the mechanism, not just that the field
  compiles (WO-101's own standing lesson: codec/field correctness is not
  proof a behaviour crosses the wire).

### 4.2 The named risk — the co-location boundary — stability chosen deliberately

Every number here (60/90/10) is a first guess, not a measurement — stated
plainly so it is not mistaken for one. The asymmetric enter/exit band plus
a 10 s dwell is a deliberate stability-over-responsiveness choice: the
prompt's own instruction for this phase. What was NOT built, and why:

* **No live tuning knobs for the three constants** (`togetherEnterM`/
  `togetherExitM`/`togetherDwellS`) — they are set only in
  `KCD2MP.wo1025`'s Lua table, no `#KCD2MP_Set...` function or console
  command. A real gap against Phase 5's radius-earning spirit: the
  co-location band should be tunable from the field the same way the
  authority radius is. Not done this session; flagged, not hidden.
* **No measurement of how often the boundary is actually crossed** in real
  play, or whether 10 s dwell feels right versus annoying. §5 names this.

### 4.3 What Phase 4 does NOT attempt

* A player standing exactly on the 60/90 m boundary and drifting is still
  handled correctly (dwell absorbs it) — but nothing renders a UI cue for
  "together" vs "apart"; a player only sees its effects (NPCs behaving
  differently), not the state itself. `mp_wo102_status`-style visibility for
  `together` was not added — another stated gap, cheap for a future session.
* Multi-player (>2) co-location is out of scope, consistent with the whole
  WO's 2-player framing (durable context: two known players do not need
  anti-cheat-shaped ownership rotation). "Nearest peer ghost" degenerates
  correctly to "the only peer ghost" in the 2-player case this was built and
  tested against; it was not tested against 3+.

### 4.4 Wire compatibility (Phase 4)

No relay packet-shape change — `CombatRole` (0x25) is unchanged, still one
byte, still broadcast on every readiness/disconnect event exactly as before;
the idle timeout changes WHEN a disconnect is detected, not what is sent.
The `KcdMp.Relay.Tests` suite (now 13 cases) remains the standing gate
`Build-Installer.ps1` runs before publish.

## 6. Live solo field session (2026-09-18, observed)

Driven from the coding shell against the maintainer's own running game
(Modding Tools build, DLL injected, save loaded, connected, solo — no
peer). Every command went through the real console
(`ExecuteString`→`kcd.log`); every result below is read from `kcd.log` or
`kcdmp-native.mirror.log`, not inferred. This is the first time ANY of
WO-102.5's native code, or WO-102's pause lever, has run against a live
game.

### 6.1 The pause lever — reliability is materially lower than WO-102's sample suggested

`mp_probe_npc_pause` run **8 times** against 8 different ambient NPCs
(the probe always targets the nearest eligible one, so repeat runs picked
whatever was nearest at the time):

| # | NPC | verdict (step 3, 3 s hold) | off_target_m | resume movement (step 5) |
|---|---|---|---|---|
| 1 | `ttkc_man_5` | HELD | 0.00 | 0.00 (NPC was idle throughout — inconclusive) |
| 2 | `karavanyVeSvete_merchantCaravan_worker_1` | **SNAPPED BACK** | 1.96 | n/a |
| 3 | `karavanyVeSvete_merchantCaravan_worker_2` | HELD | 0.00 | 3.50 (clean) |
| 4 | `ttkc_bailiffSon` | HELD | 0.00 | 4.77 (clean) |
| 5 | `ttkc_man_13` | **SNAPPED BACK** | 1.90 | 0.07 |
| 6 | `rvacka_apprentice_3` | HELD | 0.00 | 0.00 (idle — inconclusive) |
| 7 | `karavanyVeSvete_merchantCaravan_worker_1` (again) | HELD | 0.00 | 0.00 (idle) — but 0.7 m drift observed between steps 3 and 4 |
| 8 | `ttkc_man_25` | **SNAPPED BACK** | 0.64 (partial) | 4.54 (clean) |

**5/8 HELD (62.5%), 3/8 SNAPPED BACK (37.5%).** WO-102's own solo probe
reported 8/8 (100%) HELD across three NPCs. This is not that result, and
the difference is not a per-NPC-class property: run 2 and run 7 targeted
**the same NPC** (`karavanyVeSvete_merchantCaravan_worker_1`) and got
**opposite verdicts**. The failure looks timing/state-dependent — plausibly
related to WO-102 §3.5's own caution that the pause is a refcounted,
per-context suspension ("an engine suspend in another context is not undone
by ours") — not a simple "this NPC type never holds" rule.

**What this does and does not test.** The probe calls
`wh_ai_PauseNPC`/`wh_ai_ResumeNPC` directly — the same engine command the
real pause lever (`mp_wo102_pause`/`mp_wo102_resume`) wraps, fired the same
way (once, per NPC). It does NOT exercise the lever's own call site (a
puppet START/RELEASE under host authority with a live cross-machine
stream) or a COMBAT scenario specifically — solo has no puppets, so that
remains untested. But since the lever and the probe drive the identical
engine mechanism, a 37.5% failure rate on ambient NPCs is directly relevant
evidence about what the lever can be expected to do, not a tangential
result.

**Assessment, not yet acted on**: this measurably weakens the case for
shipping `mp_authority_pause_on` **on** by default (Phase 1's decision,
based on WO-102's 8/8). It does not necessarily argue for flipping it
off either — WO-102 §8's own accounting says pause-off trades this for
*continuous* brain-vs-stream contention on every fought NPC, which a
62.5%-reliable suppression is still likely better than. This is exactly the
kind of call the maintainer should make with this evidence in hand, not one
this session should make unilaterally by editing the shipped default after
the fact. Flagged, not changed.

Separately observed: `MP-SUMMARY-MOD auth_pauses=0 auth_resumes=0` for the
whole session — confirms the probe's direct `ExecuteCommand` calls do NOT
go through `mp_auth_log`'s counters (by design, it is a standalone
diagnostic), so `auth_pauses`/`auth_resumes` measure only the real lever's
own puppet-triggered pauses, which a solo session cannot produce.

### 6.2 The native NPC scan — first live run, and it is clean

`mp_npc_scan_native_on`. `kcdmp-native.mirror.log`:

```
NPCSCAN: class registry resolved NPC=... NPC_Female=... Horse=...
NPCSCAN: first scan OK total=37079 vptrOk=37079 vptrBad=0 matched=39 nameRejects=2 truncated=0
```

**37,079 entities walked, zero vptr mismatches.** The `gEnv`/`pEntitySystem`
RVA read (§2.1), the entity iterator vtable offsets, and the
`CEntity::vftable` gate all check out against a real, fully-loaded game
world on the first attempt. No crash, no refusal. `agent.log` itself was
not reachable this session (under the sandbox-redirected `%LOCALAPPDATA%`
path — a standing constraint, not new), so the pipe round-trip's `dur_ms`
was not observed; `kcd.log`'s `MP-NPCSCAN dir=consume verdict=native
pushed=N resolved=N` confirmed `pushed == resolved` on every sample (agent
push → Lua `GetEntityByName` resolution, 100%).

**Known-answer check** (`mp_npc_scan_compare`): `only_lua=0` — the
pass/fail gate for trusting the scan at all. Every NPC the Lua enumerate
found was also in the native set. `only_native=16` looked high at first,
and turned out to be a **real bug in the compare tool itself**, not the
scan: `KCD2MP_NpcScanCompare` hardcoded `KCD2MP.npcSync.radius` (30 m, the
claim-model bound) for its Lua-side walk regardless of authority state,
while the native scan is requested at `KCD2MP.wo1025.authorityRadius`
(45 m default) — comparing two different radii. `only_lua=0` was never
affected (a 30 m Lua set is trivially a subset of a 45 m native one), so
the safety-critical verdict was correct throughout; only the `only_native`
count was uninterpretable. **Fixed** in `kdcmp.lua` (now uses the same
radius logic as `mp_npc_rescan` itself) — not yet redeployed to this live
session (would need a pak rebuild and a game restart mid-session, not done
to avoid disrupting it) or reverified live.

### 6.3 The radius runbook, partially earned

Solo, one location (a town centre — bailiff's son, an innkeeper, a
wedding, caravan workers, apprentices all present), native scan on:

| authority radius | NPCs tracked (uncapped) |
|---|---|
| 45 m (default) | 39–43 |
| 90 m | 56–57 |
| 150 m | **78** |

No crash, no truncation, no `MP-AUTHORITY-VIOLATION`, at any radius,
including 150 m in what reads as a genuinely busy area — the case §3.3
worried a dense town would fail first. **A real cost-model finding**:
`total_walked` in the native scan (37,079) does not change with radius —
the native walk's own cost is independent of how far it is asked to look;
only the number of entities that PASS the distance filter (39→57→78 above)
changes. So the cost concern for a larger radius is not "the scan gets more
expensive" — it is "more NPCs get tracked and (before culling) streamed."
This narrows §3.3's open question meaningfully, though it is still not the
p95 emit-tick-spacing / packets-per-second measurement the runbook asks
for (no FPS or frame-time counter was accessible this session either).

**Culling, quantified live**: at 150 m, `tracked=78 culled=56` — only
**22 of 78 (28%) NPCs were actively streaming** at any moment; the other 56
were owned but quiet. `WO1025-CULL re-entry <name>` fired correctly during
the session (an NPC crossed back into `cullRadius` and streamed fresh, as
designed). This is live confirmation of Phase 3's central cost claim: culling
is genuinely what makes the larger radius affordable, by a wide margin, in
this location.

Not run: village-vs-town comparison (only one location, a town, was
tested), `mp_npc_cull_off` at a large radius (the "no culling" control), and
the fight (§3 of the runbook) — solo time did not extend that far this
session.
